# Pointer: Client-Server Protocol

Protocol version: **1**

This document specifies the WebSocket protocol between the desktop core and the backend, the session event model it carries, and the executor operations.
REST endpoints are listed in section 9 for orientation; their exact schemas come from the generated OpenAPI document.

## 1. Transport

- Endpoint: `wss://<host>/ws` (`ws://` only in local development).
- Authentication: `Authorization: Bearer <accessToken>` header on the upgrade request.
- Frames: UTF-8 text frames, one JSON message per frame.
- Keep-alive: the server sends WebSocket ping frames every 20 seconds. A connection without a pong for 60 seconds is closed.
- One connection per device. A new connection with the same `deviceId` replaces the old one, which is closed with code `4409`.

### 1.1 Close codes

| Code | Meaning | Client action |
|---|---|---|
| `1000` | Normal closure | Reconnect only if still signed in. |
| `4400` | Protocol error (malformed message, unknown type) | Report a bug, reconnect. |
| `4401` | Token missing, invalid or expired | Refresh the access token, reconnect. |
| `4403` | Account disabled or device revoked | Sign out. |
| `4409` | Replaced by a newer connection of this device | Do not reconnect. |
| `4426` | Unsupported protocol version | Ask the user to update the app. |

### 1.2 Reconnect

Exponential backoff starting at 1 second, doubling up to 30 seconds, with В±20% jitter. Reset after a connection stays up for 60 seconds.

## 2. Envelope

Every message has the same shape:

```json
{
  "type": "exec.request",
  "id": "0193a5c2-7f1e-7b3a-9c4d-2e8f1a6b5c3d",
  "replyTo": null,
  "payload": { }
}
```

| Field | Description |
|---|---|
| `type` | Message type, `group.name`. |
| `id` | Unique message id (UUIDv7), generated by the sender. |
| `replyTo` | Id of the message this one answers, if any. |
| `payload` | Type-specific body. |

Conventions:

- Field names are `camelCase`. Timestamps are ISO 8601 UTC strings.
- All ids are UUIDv7 strings. Examples in this document abbreviate them as `ses_01JC...`, `itm_01JC...` and so on for readability; the prefixes are not part of real ids.
- File paths in executor messages are relative to the project root and use `/` as separator.
- Unknown fields must be ignored. Unknown message types are answered with `error` and otherwise ignored.
- Binary content (relay bodies) is base64-encoded.

### 2.1 `error`

Sent by either side in response to a message that cannot be processed.

```json
{ "code": "session_not_found", "message": "Session 0193... does not exist", "retryable": false }
```

## 3. Handshake

The first message after connecting must be `hello` from the client. The server answers with `welcome` or closes the connection.

### 3.1 `hello` (client в†’ server)

```json
{
  "protocolVersion": 1,
  "deviceId": "dev_01JC3Y...",
  "deviceName": "Home PC",
  "clientVersion": "0.1.0",
  "platform": { "os": "windows", "osVersion": "10.0.26200", "shell": "powershell" },
  "capabilities": ["viewer", "executor", "relay"],
  "projects": ["prj_01JC..."],
  "undeliveredResults": [ ]
}
```

| Field | Description |
|---|---|
| `capabilities` | `viewer`: receives session events. `executor`: performs executor operations. `relay`: performs LLM relay requests. |
| `projects` | Projects mapped to a local path on this device. The device can execute only for these. |
| `undeliveredResults` | `exec.result` payloads finished while disconnected (see 6.4). |

### 3.2 `welcome` (server в†’ client)

```json
{
  "connectionId": "con_01JC...",
  "serverVersion": "0.1.0",
  "userId": "usr_01JC...",
  "limits": { "maxMessageBytes": 4194304, "maxToolOutputBytes": 262144 }
}
```

### 3.3 `device.projects_changed` (client в†’ server)

Sent when the user maps or unmaps a project on the device.

```json
{ "projects": ["prj_01JC...", "prj_01JD..."] }
```

### 3.4 `device.tools` (client → server)

Sent after `welcome` and whenever the tools of the device's MCP servers change ([ADR 0010](adr/0010-mcp-servers-on-the-device.md)). The list replaces the previous one for this device. Server configuration never leaves the device.

```json
{
  "tools": [
    {
      "server": "github",
      "name": "search_issues",
      "description": "Search issues",
      "inputSchema": { "type": "object", "properties": { "query": { "type": "string" } } },
      "readOnly": true
    }
  ]
}
```

The backend exposes each tool to the model as `mcp__<server>__<name>`, in every mode if `readOnly` is set and only in Agent mode otherwise, with the default policy `ask`.

### 3.5 `auth.refresh` (client в†’ server)

Sent with a new access token before the current one expires. The server answers with `auth.refreshed` or closes with `4401`.

```json
{ "accessToken": "eyJ..." }
```

## 4. Session subscriptions

### 4.1 `session.subscribe` (client в†’ server)

```json
{ "sessionId": "ses_01JC...", "afterSeq": 41 }
```

The server replies with `session.subscribed`, then replays every stored event with `seq > afterSeq` in order, then sends `session.snapshot` for items still in progress, then streams live messages.
`afterSeq: 0` replays the whole log. The UI normally loads history through REST and subscribes with the last `seq` it has.

### 4.2 `session.subscribed` (server в†’ client)

```json
{ "sessionId": "ses_01JC...", "lastSeq": 57, "status": "running" }
```

### 4.3 `session.unsubscribe` (client в†’ server)

```json
{ "sessionId": "ses_01JC..." }
```

### 4.4 `session.event` (server в†’ client)

A stored event of the session log.

```json
{
  "sessionId": "ses_01JC...",
  "seq": 42,
  "occurredAt": "2026-11-02T10:15:30.120Z",
  "event": { "kind": "item.created", "turnId": "trn_01JC...", "item": { } }
}
```

`seq` increases by exactly 1 per session. A client that sees a gap re-subscribes with its last contiguous `seq`.

### 4.5 `session.delta` (server в†’ client)

A transient streaming fragment. Not stored, has no `seq`.

```json
{ "sessionId": "ses_01JC...", "itemId": "itm_01JC...", "field": "text", "delta": "Let me look at " }
```

`field` is `text` for assistant messages and reasoning, `arguments` for tool-call arguments, `output` for streaming command output.

### 4.6 `session.snapshot` (server в†’ client)

The accumulated state of an in-progress item, sent after replay so a reconnecting client can continue applying deltas.

```json
{ "sessionId": "ses_01JC...", "item": { } }
```

### 4.7 `sessions.changed` (server в†’ client)

Sent to every viewer connection of the user when a session is created, renamed, archived, deleted or changes status, so session lists stay current without subscribing to each session.

```json
{ "sessionId": "ses_01JC...", "projectId": "prj_01JC...", "change": "status", "status": "waiting_for_approval" }
```

## 5. Session event model

### 5.1 Session status

| Status | Meaning |
|---|---|
| `idle` | No turn running. |
| `running` | A turn is calling the model or executing tools. |
| `waiting_for_approval` | A tool call waits for the user. |
| `waiting_for_executor` | A tool call waits for the executor device to come online. |
| `error` | The last turn failed. The user can retry or send a new message. |

### 5.2 Items

Common fields:

```json
{ "id": "itm_01JC...", "type": "tool_call", "turnId": "trn_01JC...", "status": "completed", "createdAt": "...", "completedAt": "..." }
```

Item status: `in_progress`, `completed`, `failed`, `cancelled`.

| Type | Specific fields |
|---|---|
| `user_message` | `text`, `attachments` (`[{ "kind": "file", "path": "src/App.tsx", "content": "..." }]` or `{ "kind": "image", "attachmentId": "...", "mediaType": "image/png" }`), `mode`, `planItemId` (set when the message was created by approving a plan) |
| `assistant_message` | `text`, `step` |
| `reasoning` | `text` (when the provider streams reasoning) |
| `tool_call` | `step`, `toolName`, `arguments`, `argumentsJson`, `providerCallId`, `toolStatus`, `result`, `error`, `output`, `fileChanges`, `resultText`, `approvalId`, `approvalPreview` |
| `plan` | `step`, `summary`, `steps` (`[{ "title": "...", "details": "..." }]`), `approval` (`pending`, `approved`, `rejected`), `providerCallId`, `argumentsJson`, `resultText` |
| `compaction_summary` | `text`, `replacedItemCount` |

A user message sent while a turn runs is created with `turnId: null` (queued). At the next step boundary it is attached to the running turn if it was sent in the same mode, otherwise it starts the next turn.

A `plan` item is created when the model calls the server-side `propose_plan` tool in Plan mode; the turn then ends. Approving it switches the session to Agent mode and starts a turn. Any other user message rejects pending plans. See [ADR 0009](adr/0009-context-compaction-and-plan-approval.md).

A `compaction_summary` item is produced by a turn of kind `compaction` (manual) or inside a message turn before a model call (automatic). The model's context starts from the latest completed summary.

Rewinding (`POST /sessions/{id}/rewind` with `turnId`, `restoreFiles`, `force`) marks the turn and every later turn as rewound. With `restoreFiles`, agent file changes from those turns are first checked with a dry-run `pointer.restore_file` per file and then restored; a file changed since fails the whole request with `file_modified` unless `force` is set. Only changes made by write tools are restored, not side effects of `run_command`. The response returns the restored paths and the text of the rewound user message.

`toolStatus` of a tool call:

| Value | Meaning |
|---|---|
| `pending` | Arguments are streaming or the call is queued. |
| `awaiting_approval` | Waiting for the user. |
| `running` | Dispatched to the executor. |
| `succeeded` | Executor returned a result. |
| `failed` | Executor returned an error, or the call timed out. |
| `denied` | Blocked by a policy, by the mode or by the user. |
| `cancelled` | The turn was cancelled while the call was pending or running. |

### 5.3 Event kinds

| Kind | Payload | Emitted when |
|---|---|---|
| `turn.started` | `turnId`, `turnKind` (`message`, `compaction`), `mode`, `modelId` | A turn begins. |
| `turn.completed` | `turnId`, `reason` (`completed`, `cancelled`, `failed`, `step_limit`, `interrupted`), `usage`, `error` | A turn ends. |
| `item.created` | `turnId`, `item` | An item starts. Streaming deltas for it may follow. |
| `item.updated` | `item` | An item changes: a tool call moving to `awaiting_approval` or `running`, a queued user message attached to a turn, a plan approved or rejected. Carries the full item. |
| `item.completed` | `item` | An item reaches its final state. Carries the full item. |
| `approval.requested` | `approvalId`, `itemId`, `preview` | A tool call needs approval. |
| `approval.resolved` | `approvalId`, `decision` (`approved`, `denied`), `scope` (`once`, `session`), `message` | The user answered. |
| `file.changed` | `changeId`, `itemId`, `path`, `changeKind` (`created`, `modified`, `deleted`), `linesAdded`, `linesRemoved` | A tool call changed a file. |
| `file.reverted` | `changeIds`, `path` | The user reverted changes to a file. |
| `session.rewound` | `turnId`, `turnIds` | The user rewound the session to before `turnId`. Items of all `turnIds` leave the history and the model's context. |
| `status.changed` | `status` | Session status changes. |
| `usage.updated` | `contextTokens`, `contextWindow`, `totalInputTokens`, `totalOutputTokens`, `estimatedCost` | After each model call. `estimatedCost` is null until a call is made with a model that has prices (CTX-6). |
| `session.updated` | `title`, `mode`, `model`, `autoApprove`, `archived`, `worktree` | Session settings change, including worktree creation, merge and discard. |

Approval `preview`:

```json
{ "kind": "diff", "path": "src/App.tsx", "unifiedDiff": "@@ -1,4 +1,5 @@ ..." }
```

```json
{ "kind": "command", "command": "npm install zod", "workingDirectory": "." }
```

```json
{ "kind": "tool", "server": "github", "tool": "create_issue", "arguments": { "title": "..." } }
```

## 6. Execution

### 6.1 `exec.request` (server в†’ client)

```json
{
  "callId": "cal_01JC...",
  "sessionId": "ses_01JC...",
  "projectId": "prj_01JC...",
  "operation": "edit_file",
  "arguments": { "path": "src/App.tsx", "oldText": "foo", "newText": "bar" },
  "dryRun": false,
  "timeoutMs": 30000,
  "worktree": "pointer/01a1a7ea"
}
```

`worktree` is present only for sessions with an active worktree ([ADR 0011](adr/0011-session-worktrees.md)). The client then uses `<app data>/worktrees/<sessionId>` as the root instead of the project folder.

The client rejects with `exec.result` status `rejected` if the project is not mapped on the device, the operation is unknown, a path resolves outside the root, or the session worktree does not exist (`worktree_missing`).

### 6.2 `exec.output` (client в†’ server)

Streaming output of a running operation, currently only `run_command`.

```json
{ "callId": "cal_01JC...", "stream": "stdout", "data": "added 1 package in 2s\n" }
```

### 6.3 `exec.result` (client в†’ server)

```json
{
  "callId": "cal_01JC...",
  "status": "succeeded",
  "result": { },
  "error": null,
  "fileChanges": [
    { "path": "src/App.tsx", "changeKind": "modified", "before": "...", "after": "...", "linesAdded": 3, "linesRemoved": 1 }
  ],
  "durationMs": 12
}
```

| Status | Meaning |
|---|---|
| `succeeded` | Operation completed. `result` holds the operation result. |
| `failed` | Operation ran and failed (file not found, text not matched, non-zero exit is **not** a failure for `run_command`). `error` holds `code` and `message`. |
| `rejected` | Operation refused by the client before running. |
| `timeout` | Operation exceeded `timeoutMs` and was stopped. |
| `cancelled` | Stopped by `exec.cancel`. |

For `dryRun: true`, file operations return the diff in `result.preview` and do not touch the disk. `fileChanges` is empty.

### 6.4 `exec.cancel` (server в†’ client)

```json
{ "callId": "cal_01JC..." }
```

The client stops the operation (killing the process tree for commands) and answers with `exec.result` status `cancelled`.

### 6.5 Disconnects during execution

- Operations keep running on the client while it reconnects. Their results are buffered and sent in `hello.undeliveredResults`.
- The backend waits for a running call for its remaining timeout plus a 30 second grace period. Then the call fails with code `executor_disconnected`, and the model is told the outcome is unknown.
- The backend never retries a non-read-only operation automatically.

## 7. Executor operations

### 7.1 Model-facing tools

Arguments and results are what the model sees. The agent may receive a truncated result if it exceeds `maxToolOutputBytes`.

| Operation | Arguments | Result |
|---|---|---|
| `list_directory` | `path` | `entries: [{ name, kind: "file" \| "directory", size }]` |
| `read_file` | `path`, `offset?` (first line, 1-based), `limit?` (lines) | `content`, `totalLines`, `truncated` |
| `glob` | `pattern`, `path?` | `paths: []`, `truncated` |
| `grep` | `pattern` (regex), `path?`, `glob?`, `caseInsensitive?`, `contextLines?`, `maxResults?` | `matches: [{ path, line, text }]`, `truncated` |
| `write_file` | `path`, `content` | `created` (boolean) |
| `edit_file` | `path`, `oldText`, `newText`, `replaceAll?` | `replacements` |
| `run_command` | `command`, `workingDirectory?`, `timeoutMs?` | `exitCode`, `output` (combined, tail if truncated), `truncated` |
| `web_fetch` | `url` (http or https), `maxChars?` (default 20000, at most 25000) | `url` (after redirects), `status`, `contentType`, `content` (HTML converted to text), `truncated` |

Notes:

- `edit_file` fails with `text_not_found` if `oldText` does not occur, and with `text_not_unique` if it occurs more than once and `replaceAll` is false.
- `glob` and `grep` respect `.gitignore` and skip binary files.
- `run_command` runs in PowerShell with the project root (or `workingDirectory` within it) as the current directory.
- `web_fetch` runs on the device, so it reaches the same hosts as the user's browser, including local dev servers. It refuses non-text content with `unsupported_content`. It is offered in every mode and asks for approval by default, with a `fetch` preview holding the URL.

MCP tools reach the executor as operation `mcp.call` with `server`, `tool` and `arguments`. The result is `content` (text blocks joined, other blocks as placeholders) and `structuredContent` when the server returns it. A result with `isError` becomes a failure with code `tool_error`.

### 7.2 Internal operations

Used by the backend itself, never exposed to the model. Names start with `pointer.`.

| Operation | Arguments | Result |
|---|---|---|
| `pointer.project_context` | none | `rulesFile` (`{ name, content }` or null), `gitBranch`, `isGitRepository` |
| `pointer.worktree_create` | none | `branch`, `baseBranch`, `path`. Creates the worktree on a new branch from `HEAD`. Fails with `not_a_git_repository`, `not_repository_root`, `detached_head` or `worktree_exists`. |
| `pointer.worktree_status` | `baseBranch` | `path`, `branch`, `baseBranch`, `commitsAhead`, `uncommittedFiles`, `baseCheckedOut` |
| `pointer.worktree_merge` | `baseBranch`, `message` | `merged`, `commits`. Commits pending changes with `message`, merges the branch with `--no-ff` into the project folder, then removes the worktree and the branch. Fails with `base_not_checked_out`, `commit_failed` or `merge_conflict` (the merge is aborted). |
| `pointer.worktree_discard` | none | `discarded`. Removes the worktree and deletes the branch. |
| `pointer.restore_file` | `path`, `content` (null to delete), `expectedContent` (null if the file should not exist), `force` | `restored` (boolean), fails with `file_modified` if the current content differs from `expectedContent` and `force` is not set. With `dryRun` it only performs the check. |

## 8. LLM relay

### 8.1 `relay.request` (server в†’ client)

```json
{
  "relayId": "rly_01JC...",
  "providerId": "prv_01JC...",
  "method": "POST",
  "url": "http://localhost:11434/v1/chat/completions",
  "headers": { "Content-Type": "application/json" },
  "body": "eyJtb2RlbCI6..."
}
```

The client rejects the request with `relay.error` code `host_not_allowed` unless the host is a loopback address or approved by the user on this device.

### 8.2 Response messages (client в†’ server)

| Type | Payload |
|---|---|
| `relay.response.start` | `relayId`, `status`, `headers` |
| `relay.response.chunk` | `relayId`, `data` (base64) |
| `relay.response.end` | `relayId` |
| `relay.error` | `relayId`, `code` (`host_not_allowed`, `connection_failed`, `timeout`, `cancelled`), `message` |

### 8.3 `relay.cancel` (server в†’ client)

```json
{ "relayId": "rly_01JC..." }
```

## 9. REST overview

All endpoints are under `/api/v1`, authenticated with the access token unless marked public.

| Area | Endpoints |
|---|---|
| Auth | `POST /auth/register` (public), `POST /auth/login` (public), `POST /auth/refresh` (public), `POST /auth/logout` (public, takes the refresh token), `GET /auth/github/authorize-url` (public), `POST /auth/github/callback` (public), `POST /auth/github/link`, `PUT /auth/password` |
| User | `GET /me`, `PATCH /me`, `GET /me/settings`, `PUT /me/settings`, `GET /commands`, `POST /commands`, `PUT /commands/{id}`, `DELETE /commands/{id}` |
| Devices | `GET /devices`, `PATCH /devices/{id}`, `DELETE /devices/{id}` |
| Providers | `GET /providers`, `POST /providers`, `PATCH /providers/{id}`, `DELETE /providers/{id}`, `POST /providers/{id}/test`, `POST /providers/{id}/models/refresh`, `PATCH /providers/{id}/models/{modelId}` |
| Projects | `GET /projects`, `POST /projects`, `PATCH /projects/{id}`, `DELETE /projects/{id}`, `GET /projects/{id}/settings`, `PUT /projects/{id}/settings` |
| Sessions | `GET /projects/{id}/sessions`, `POST /projects/{id}/sessions`, `GET /sessions/{id}`, `PATCH /sessions/{id}`, `DELETE /sessions/{id}`, `GET /sessions/{id}/items`, `GET /sessions/{id}/events?afterSeq=` |
| Attachments | `POST /sessions/{id}/attachments` (raw PNG, JPEG, GIF or WebP body, at most 5 MB), `GET /sessions/{id}/attachments/{attachmentId}` |
| Turns | `POST /sessions/{id}/messages`, `POST /sessions/{id}/cancel`, `POST /sessions/{id}/compact`, `POST /sessions/{id}/plans/{itemId}/approve` |
| Approvals | `POST /sessions/{id}/approvals/{approvalId}` with `decision`, `scope`, `message` |
| Review | `GET /sessions/{id}/changes`, `GET /sessions/{id}/changes/file?path=`, `POST /sessions/{id}/changes/revert` with `path` and `force`, `POST /sessions/{id}/rewind` with `turnId`, `restoreFiles` and `force` |
| Worktrees | `POST /sessions/{id}/worktree` (before the first message), `GET /sessions/{id}/worktree`, `POST /sessions/{id}/worktree/merge` with `message`, `POST /sessions/{id}/worktree/discard` |
| Permissions | `GET /permissions`, `PUT /permissions`, `GET /projects/{id}/permissions`, `PUT /projects/{id}/permissions` |
| Tools | `GET /tools` |

`POST /sessions/{id}/messages` accepts an `Idempotency-Key` header so a retried request never starts a second turn.

## 10. Versioning

- The protocol version is an integer exchanged in `hello`. The server supports the current and the previous version.
- Adding message types, event kinds, optional fields or enum values is backward compatible and does not change the version. Clients must tolerate unknown values.
- Removing or changing the meaning of a field requires a new version.
