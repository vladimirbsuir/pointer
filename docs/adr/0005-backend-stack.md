# 0005. Backend stack: Java 25, Spring Boot 4, PostgreSQL

Status: Accepted

## Context

The backend is a monolith that hosts sessions, the agent loop, provider integration, persistence and, later, semantic search.
It holds many long-lived streaming connections: WebSocket to clients and HTTP streams to providers.

## Decision

- **Language and framework:** Java 25 (LTS), Spring Boot 4.
- **Build:** Gradle with Kotlin DSL.
- **Base package:** `dev.pointer`.
- **Database:** PostgreSQL with the pgvector extension. Schema migrations with Flyway.
- **Client connection:** WebSocket with a JSON message protocol specified in `docs/`.
- **LLM access:** a thin OpenAI-compatible client of our own behind the provider interface (see [0002](0002-openai-compatible-byok-providers.md)). Spring AI may be used for parts where it fits, but the agent loop does not depend on it.
- **Concurrency:** virtual threads for blocking I/O.
- **API documentation:** OpenAPI generated by springdoc.
- **Local run:** Docker Compose in `infra/` for PostgreSQL. Cloud deployment comes later.

## Consequences

- Virtual threads let streaming and tool round trips be written as plain sequential code.
- Owning the LLM client keeps full control of streaming tool calls and provider quirks, which are central to the product.
- pgvector keeps semantic search in the same database, with no separate vector store.

## Rejected alternatives

- **Maven:** works equally well. Gradle chosen for concise build scripts.
- **Spring AI as the core of the agent loop:** convenient, but hides the loop that is the main subject of the project.
- **A separate vector database:** unnecessary at this scale.
